# 响应链路优化：范围、价值与验证

本轮基线是开始优化前的工作树，**已包含 999s/999s 失败采样和中断计数修复**，不是 Git HEAD。
不修改生产配置、数据库结构或运行中的服务。

## 1. 价值判定与实际范围

| 项目 | 价值 / 风险判断 | 决定 |
|---|---|---|
| 102 临时响应后重复 Flush | 正确性问题：Go 服务端会提前提交默认 200，覆盖后续真实错误状态 | 修复，并验证真实 HTTP/1.1 / HTTP/2 |
| 下游写阻塞被计为上游超时 | 正确性问题：健康上游可能被关闭、降权及记入 999 惩罚 | 修复，计时只覆盖上游 Read 等待 |
| 错误摘要解析两次 | 每次错误都付出重复 JSON/文本处理和分配成本 | 共享一次解析结果；空 masking 规则直接返回 |
| SSE 首块刷新两次 | 数据已到内存，单独刷新空响应头没有等待收益 | 首块头和数据一次刷新；保留空流最终刷新 |
| 禁用临时响应仍分配对象、加锁 | 实现简单，可稳定消除一次分配 | 返回 nil，收尾与提交方法兼容 nil |
| 遮罩响应同步等待弃用 body | 仅字节限制不能阻止停滞或涓流拖延错误返回 | 未完整读取时最多清理 64KiB / 50ms，然后关闭 |
| 错误预览增加更短总超时 / 跳过正文 | 会改变关键词禁用、冷却、遮罩与诊断语义 | 暂缓；保留 2048 字节 / EOF 的预览规则 |
| 统计锁合并、脏 Key 快照 | 收益依赖 Key 数量和并发，涉及重置/版本/持久化一致性 | 暂缓，单独压测后再做 |

此外收敛 `handleUpstreamResponse` 的重复交付分支，只在实际透传时构造预览回放 reader；已知读取完整的错误体直接回放原始字节，不再次读取已关闭的上游 body。删除未使用的旧 `responsePreview` 实现。

## 2. 实现边界

### 临时响应与流式刷新

`net/http` 的 `WriteHeader(102)` 已负责发送 informational headers。紧接着调用 `Flush` 会隐式提交最终 200；现在不再这样做。最终 200/502/504 的状态与正文经过真实 HTTP/1.1、HTTP/2 服务端验证。

普通流式响应在首块到达后同时提交头和正文，再刷新一次。每个后续块仍立即刷新，不做 SSE 合并、不增加首 token 等待。合法空流仍刷新最终头。刷新通过 `http.ResponseController` 优先读取 `FlushError`，支持 `Unwrap`，不支持刷新时保持普通写出行为。仅 Flush 失败也记为下游中断；先前已确定的上游 HTTP/读取失败不被覆盖。

### 上游读取超时

`body_timeout` 只约束正在执行的上游 `Read`。等待客户端 `Write/Flush` 不再消耗该预算，不会因为客户端慢而惩罚 Key。成功响应的整包耗时统计依然包含既有下游背压，这与超时归因是两回事。

每个响应体复用一个延迟创建的 timer：记录当前读取 deadline，回调检查是否仍在读取；旧回调不会过早关闭下一次读取。正常分块不逐块创建 timer/goroutine，也不逐块重置 timer 堆。EOF、显式 Close、真实读取超时保持独立；超时唤醒出的 EOF 仍是失败，客户端主动关闭不冒充上游超时。

这项修复增加了读取阶段同步成本，见下方微基准，不把它描述成无成本优化。

### 错误预览、规则和清理

- 同一份解码后的预览只生成一次文本摘要，供健康分类与遮罩匹配使用；规则顺序、Retry-After、自动禁用优先级和冷却延长保持原语义。
- 原始压缩字节用于透传，不能用解码后的诊断文字替换上游正文。诊断解压仍限制为 64KiB。
- 已在预览阶段读到 EOF 的遮罩响应无需再 drain，也不会新增清理 timer。
- 对未读完且已确定要丢弃的遮罩 body，新增一个总清理预算 timer；50ms 到期即调用 Close，不因涓流进度延长。它只用于错误清理，不进入成功响应或逐块热路径。实际唤醒时间仍受运行时调度及 Body.Close 行为影响。
- 超过预算会放弃该上游连接的复用；这是避免确定的错误响应继续等待所作的权衡。清理不会改变真实上游状态，不再生成第二条失败或中断记录。
- 不改变非幂等重放约束、供应商/聚合重试策略、全局尝试预算、取消归因和 999 秒惩罚规则。
- 未缩短错误预览本身的等待：慢错误体仍可能阻塞到现有上游读取超时。这是明确保留的剩余限制，不应把 50ms 清理预算理解为所有错误响应的总延迟上限。

## 4. 验证

- 全量 `go test ./...`、`go test -race ./...`、`go vet ./...`、`go build ./...`。
- 关键 timer/临时响应/清理回归在 `-race` 下重复 10 次。
- 真实 HTTP/1.1 和 HTTP/2 收到 102 后保持最终 200/502/504；真实网络上游的弃用错误体由预算 Close 解除等待。
- 慢下游不关闭健康上游；真正阻塞读取仍超时；旧 timer 回调、读取以外的回调及显式 Close 不误判。
- 停滞和涓流错误体清理有总预算，仍只记录原始失败一次。
- SSE 各块单次刷新及空流刷新、压缩原字节回放、规则分类/遮罩优先级一致性。
- 前端现有 13 项测试通过。本轮不修改前端。

## 5. 全量修改复查

复查确认并修复两处边界，回归用例位于 `internal/gateway/response_review_test.go`：

1. **错误预览读取失败的重试开关回归**：保留原始 HTTP 状态时，不能用该状态的 failover 决策替代 `Failover.RequestError`。现在健康/计数仍保留原始 HTTP 失败，预览读失败的供应商重试独立遵循 request-error 开关，并保留非幂等请求禁止重放的限制。
2. **SSE 仅 Flush 失败被记成成功**：`Write` 可能只写入服务端缓冲区并返回成功，真正的网络错误在 `FlushError` 才出现。现在捕获该错误，普通成功候选转为中断计数；已确定的 HTTP 错误/读取失败仍只记录一次原结果。真实 HTTP/1.1 过期写 deadline 已复现该问题并验证修复，另覆盖空流、已知上游失败、无 Flush 支持及 Unwrap 包装。

修正后重新通过全量 Go 测试、`-race`、vet、构建，前端 13 项测试及生产构建；新增用例与关键计时、102、清理用例在 `-race` 下重复 10 次通过。
