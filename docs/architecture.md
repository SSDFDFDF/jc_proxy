# 架构：一致性、Key 状态与数据结构版本

本文描述控制面的一致性保障、Key 运行状态的生命周期、持久化行为，以及持久化数据的
schema 版本规则与升级方法。数据面链路与统计见 [网关链路行为](gateway-behavior.md) 和
[耗时统计与负载策略](performance-and-balancing.md)。

## 1. 配置更新的一致性

- `Service.changeMu` 覆盖配置 RMW 全过程：配置/Key 管理操作串行，两个并发的创建供应商或添加客户端 Key 操作不会相互覆盖。读取和数据面转发不等待这把锁。
- `Runtime.UpdateAndPersist` 的顺序：
  1. 克隆、校验并构建完整候选路由；
  2. 调用配置存储持久化；失败则保留原路由和健康状态，清理候选 Transport；
  3. 绑定共享 Key 状态，发布新路由和配置。不在发布后执行可能失败的持久化。
- `RefreshKeys` 在同一更新锁内读取配置，等待中的刷新不会把较新的配置替换回旧版本。
- 路由构建阶段不合并/修改已有统计 handle，候选准备失败不会提前恢复冷却中的 Key。
- 配置文件使用随机临时文件、`Sync`、原子 rename 写盘，不存在固定 `.tmp` 文件被并发写者争用的问题。
- `pgsql` 模式的运行时配置更新只写权威数据库，本地文件保持 bootstrap 身份，不再同时回写镜像文件；避免第二次写失败造成分叉。
- 文件 Key 存储的增删、替换、状态、备注都先保存新数据再提交内存。条件自动禁用写文件失败不会提前增加内存版本号，重试不会因此被误判为版本冲突。

以上保障为**单进程范围**：完整配置 PUT 仍是替换语义，不提供跨客户端/跨实例 CAS；批量 Key 操作不是跨 Key 事务。

## 2. Key 状态跨路由重建共享

Pool 保留独立的选择策略和游标，但保留的 Key 引用同一 `KeyState`，重叠的路由代次共用该供应商的锁。因此：

- 新路由能看到旧请求的 in-flight；旧请求结束时正确减回，不归零也不泄漏。
- 重建之后才返回的失败、冷却、禁用仍被当前路由看到。
- 同版本的旧存储快照不能覆盖刚发生的自动禁用。
- 新的持久化版本（如管理员启用/恢复）优先，清理旧冷却/退避。
- 选择 Key 与捕获其版本在同一临界区，防止旧请求被标记成新版本。
- 迟到的旧版本响应仍计入累计计数，但不改变新健康状态/最近错误，也不污染新版本的近期性能窗口。
- 已删除 Key 在旧池中退休，不允许旧路由重试它；再次添加使用新健康状态。

这些是进程内运行状态，不逐请求写数据库。**进程重启仍会清空未持久化的冷却/并发状态。**

Transport 由 `transportManager` 跨热更新复用（按配置区分，Transport 内部按主机管理连接），过期配置关闭空闲连接；重建路由不再丢弃全部 keep-alive 连接。

## 3. 日志脱敏与失败可见性

- 异步状态同步的正常重试与最终关闭错误统一使用 `key_id`，底层错误消息中回显的明文 Key 会被移除；错误包装保留 `errors.Is/As` 能力。
- 版本冲突/Key 已删除仍停止重试，但会留下脱敏诊断，不再静默丢弃。

## 4. 数据结构版本与升级

配置和上游 Key 存储都带版本标记：配置文件里的 `schema_version`，PGSQL Key 表旁的 `<table>_meta` 表。当前版本为 **v3**。

服务只读取当前版本，遇到旧数据直接拒绝启动并提示升级，不做在线迁移：

```text
load config failed: config schema version 2 is older than required (3): run "jc_proxy_upgrade -config <path>" to migrate, then restart
```

升级前先备份并停止所有实例，避免旧版与新版混跑。升级使用独立命令，先 dry-run 再执行：

```bash
go build -o jc_proxy_upgrade ./cmd/jc_proxy_upgrade
./jc_proxy_upgrade -config ./config.yaml -dry-run
./jc_proxy_upgrade -config ./config.yaml
```

各版本变更内容：

- **v1 → v2**：`vendors` 从按名字索引的 map 改成 `[{id, name, ...}]` 数组并生成 `id`；`aggregate.children[].vendor` 改成 `vendor_id`；上游 Key 分区从供应商名字改成 `id`（PGSQL 是 `vendor` 列改名为 `vendor_id`，单事务内完成）；移除废弃的 `vendors.*.upstream.keys` 内联 Key 字段。
- **v2 → v3**：PGSQL Key 表新增 `recent_stats JSONB`（保存近期均值和样本数），添加列与 Key 表版本标记在同一事务内完成。配置结构与 vendor ID 不变，仅更新版本标记；文件 Key 存储保留原分区、Key 和累计计数。新安装直接创建 v3。

升级命令的行为：

- 配置文件和 PGSQL 配置行都会先备份（`config.yaml.v<旧版本>.<时间戳>.bak` / `<record_key>.v<旧版本>.backup.<时间戳>` 行）。
- 命令可重复执行：已是当前版本的数据会跳过，中途失败也能重跑；拒绝覆盖比自身更新的 Key schema。
- `storage.config.driver=pgsql` 时同时迁移本地文件和数据库里的配置副本，避免重启读到旧数据。
- 迁移同时涉及文件、配置行、Key DDL 的多个提交点，**不是跨资源原子事务**。

升级后先在 `web/` 执行 `npm ci && npm run build`，再重新构建并启动服务。不要只修改 `schema_version` 跳过迁移。

**部署侧注意**：数据库 schema 必须与部署的二进制一致。v3 数据库不能被只支持 v2 的二进制启动（启动即拒绝）；旧构建也绝不能执行配置保存，否则会把 v2 载荷写回 v3 数据库行。升级数据库后应立即推送并部署包含 v3 支持的构建。

## 5. 保留边界

- 单进程控制面串行化不是多实例数据库 CAS；完整配置替换不合并客户端持有的旧副本。
- 配置与 Key 分属不同持久化操作；批量 Key 操作、删除供应商与删除其 Key 分区不是跨资源事务。
- 已进入数据库的异步状态写仍依赖存储版本条件，没有分布式事务或持久化意图日志。
- 累计统计提交结果不明、多实例全局最近五次窗口、冷却状态跨进程重启恢复均不在当前实现范围。
- Server 监听/TLS 等启动参数仍需重启，不因配置路由的安全发布而变成可热重载。
