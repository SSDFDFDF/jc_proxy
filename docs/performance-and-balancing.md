# 耗时统计与 Key 负载策略

本文描述当前实现的统计语义、三种性能感知 Key 策略、展示规则与持久化边界。
网关响应链路（超时、刷新、URL、停机等）的行为边界见 [网关链路行为](gateway-behavior.md)，
配置一致性与数据结构版本见 [架构与升级](architecture.md)。

## 1. 统计语义

统计单位是 **(vendor ID, 托管 Key) 的一次上游尝试**，不是一个客户端请求，也不是 TCP 包。
一次客户端请求若故障转移到两个 Key，会分别产生两个 Key 的样本。passthrough 不保存客户端 Key 的统计。

| 字段 | 含义 |
|---|---|
| `recent_requests` | 最近有效尝试数，上限 5，按完成顺序滚动 |
| `recent_success_count` | 窗口内成功次数：HTTP <400，完整转发至 EOF，且不是异常空响应 |
| `header_samples` / `avg_header_ms` | 窗口中头耗时/失败惩罚样本数及均值（毫秒） |
| `response_samples` / `avg_response_ms` | 窗口中整体耗时/失败惩罚样本数及均值（毫秒） |

计时起点紧邻 `http.Client.Do`，不含客户端请求体预缓冲、鉴权和 Key 选择。
头耗时含连接池等待、DNS/TCP/TLS、请求上传及上游等待，**不是首字节精确追踪，更不是 LLM 首 token 耗时**。
整体耗时计到读取 EOF，流式请求计到流结束；因读取与写出串行，包含先前的下游背压，不等于纯上游生成速度。

- HTTP 错误（含 502/504）、网络失败、重试丢弃的错误响应、上游 body 超时/断流：每次记录失败，头和整体耗时均使用 **999 秒（999000ms）**，无论是否收到响应头、是否读到 EOF。均值包含惩罚，不是纯真实延迟。
- 成功响应仍记录真实耗时。JSON/SSE 或常见推理接口的 0B 响应判失败；HEAD、OPTIONS、204/205、304、重定向和通用接口允许的空响应不误判。不解析 SSE 结束事件或业务 token。
- 客户端取消、请求体读取失败及下游写失败记录一次累计请求，不记成功/上游错误、不进入近期窗口、不更新健康或最近错误。`interrupted_count` 由 `total_requests - success_count - 各类错误计数` 推导，无新数据库列；界面单独展示，成功率分母为成功与上游失败之和。
- 成功结算前已取消的请求，即使读取返回正常 EOF、Write/Flush 未报错，也不采集耗时样本；已确认的上游失败不被后续取消覆盖。尚未发起上游请求的鉴权/上传准备失败不计 Key 尝试。
- 收到成功头之后的上游 body 超时/断流仍计入累计错误，执行 request-error 健康策略并记录网关 502 诊断；已知 HTTP 错误保留真实状态，即使错误体读取或下游交付随后失败。
- 每个 attempt 通过 `Pool.CompleteAttempt` 只结算一次，重试、masking 和下游取消不重复计数；样本、累计计数、版本和健康更新以 pool → stats 锁顺序原子提交，reset/snapshot 不会拆开一个 outcome。
- 不保存请求内容、响应内容、逐请求数据库记录或无限增长的时间序列。历史漏记不可恢复；已聚合的旧均值不伪造回填，窗口随新尝试更新。

实现：`internal/balancer/performance.go` 固定 `[5]requestSample`，无堆分配；`internal/gateway/attempt_timing.go`
统一结算。旧 Key 版本的在途结果只保留累计流量，不修改当前样本和健康状态。

## 2. 缓存与持久化

- 沿用默认 **5 秒周期**批量刷盘及关闭时最终 Flush：无变化不写，有变化随现有统计同批写入。停机顺序见 [网关链路行为](gateway-behavior.md#停机)。
- 累计计数用 delta 累加；近期统计是**覆盖快照**，不是平均值累加。只有近期窗口变化、累计计数未变时不清除最近状态码/错误。
- 明确失败时不推进 persister 基线；文件存储先成功写盘再交换内存。
- 均值与样本数保存在文件 JSON / PGSQL `recent_stats JSONB` 中，**原始五条样本只在内存**。
- 热更新复用 registry handle，仍存在的 Key 的在途请求完成后也能写回同一窗口。
- 重启后保留最后持久化的摘要作展示及策略初始参考；第一条新样本或相隔 5 分钟后的新样本开始建立新窗口，不用历史均值伪造 5 条样本。

边界：

- 无流量时保留最后的窗口，并非"最近几分钟"；不是长期监控或告警系统。
- 崩溃/SIGKILL 可能丢失最近一个尚未刷盘的窗口，与累计统计一致；没有 WAL。
- 多实例共享数据库时，该摘要是各实例最近写入的本地窗口，**不是所有实例合并后的全局最近 5 次**。
- PG 事务提交结果不明时沿用计数增量协议的幂等处理，没有分布式 exactly-once。

## 3. 性能感知策略

令 `H` 为成功样本的平均头耗时，`F` 为成功样本的平均整体耗时，`I` 为当前在途请求数，
`p = (近期成功数 + 1) / (近期尝试数 + 2)` 为拉普拉斯平滑成功率。成本越低越优先：

| 策略 | 成本 | 场景 |
|---|---|---|
| `lowest_latency` | `H × (I + 1) / p` | 流式对话、优先快速开始响应 |
| `highest_success` | `(I + 1) / p²` | 对成功率更敏感，仍考虑当前负载 |
| `adaptive` | `(0.7H + 0.3F) × (I + 1) / p²` | 相近模型/输出长度的非流式业务 |

- 展示均值包含失败的固定 999 秒惩罚；调度耗时只使用成功样本，配合近期成功率和全失败高成本降权，不把 999 秒重复代入调度公式。
- 重启后的持久化摘要没有成功耗时明细：只有全成功摘要可恢复耗时评分，混合摘要使用中性耗时和已有成功率。
- 无头耗时时使用 1000ms 初始参考；无整体耗时时用 H。策略计算的 H/F 限制在 1ms–1h，F 不小于 H；展示均值不做这个截断。
- 有样本但窗口成功数为 0 时，三种策略的基础成本统一提升到 `1e12`，避免"失败越快越被偏好"；全失败窗口的 Key 被大幅降权，而不是因为报错快就获得更多流量。在无成功候选时仍能选择可用 Key，这不是另一个硬熔断器。
- 默认仍为 `round_robin`，不会自动更改已有供应商策略。新策略仅用于托管 Key 选择；聚合供应商应在 child 上配置，后端拒绝在 aggregate 上配置却不执行它们。

## 4. 探索机制与评分衰减

1. 每次成功选择累积一份探索预算，累积 10 份可探索一次，最多保留一次额度。当前白名单没有待探索候选时保留额度，不固定在第 10 次请求消耗；预算在重叠路由代际与热更新间共享。
2. 无样本 Key 补足 2 次有效样本；5 分钟没有新样本的 Key 重新进入探索队列。按上次实际选中时间从旧到新分配机会，取消也更新尝试顺序但不记失败样本。只探索当前无在途请求的 Key。
3. 探索连续失败的退避为 1/2/4/5 分钟（上限 5 分钟），成功后清除；退避只限制探索，正常评分仍可在没有更好候选时选择该 Key。
4. 最后采样后 5–10 分钟，旧评分线性回归中性值；下一次过期采样重新建立窗口。重启无采样时间可恢复，摘要最多作为启动后 10 分钟的初始参考。
5. 探索使用真实请求，不新增后台上游调用。N 个待探索 Key 在每分钟 R 次合适选择下，一轮约需 10N/R 分钟；没有流量时不保证按分钟更新。
6. 探测与普通选择均遵守：禁用、冷却、重试排除、聚合 child 的 Key 白名单；空白名单仍禁止选择。相同成本按轮询距离打破平局。
7. 基础成本只在样本完成时重算。一次扫描同时寻找最低成本与待探索候选，每候选读取一个成本原子数，不增加逐 Key 统计锁、堆分配、计时器或后台 goroutine。

限制：5 样本的小窗口响应快但较噪；请求模型、token 数、客户端速度不一致会影响比较。
长流式响应本来就可能持续很久，不宜用整体耗时时长评价上游速度，优先考虑 `lowest_latency`。
"高成功率优先"不是绝对只选成功率最高者：并发惩罚可能让空闲候选获得流量。

## 5. 前端展示

- 密钥中心与运行统计卡片复用 `KeyRecentTiming`，以秒显示 `响应/耗时 1s/30s`（头耗时/整体耗时）。
- 不足五次按实际样本计；失败样本显示/计入 `999s/999s`；没有样本或旧摘要的缺失项显示 `—`，旁边标注窗口数与样本数；提示中区分成功真实耗时与失败惩罚。
- 累计请求包含取消/下游中断，单独显示中断次数；成功/失败与成功率不把中断误归类为上游失败。
- Key 与备注合并展示，异常列固定 260px，直接换行展示最近错误与不同的禁用原因，不再压缩成零宽隐藏。
- 运行态的空错误/启用状态具有优先权，不从旧存储记录复活已清除的错误。
- 小于 768px 使用同一套行 DOM 的卡片布局，保留全选、排序、搜索、分页、批量与单 Key 操作；按钮至少 40px 高，供应商标签横向滚动。

## 6. 实现要点与成本

- 聚合 child 的负载评分使用 `Pool.LoadTotals(allowed)`：只读并发与原子累计请求计数，支持按 child 的 Key 子集扫描，不再为评分复制完整 KeyState（原实现 100 Key 评分约需 4.9µs/21KB，现约 0.1µs/0 分配）。
- 流式复制复用独立的 4KiB `sync.Pool` 缓冲，长流不占用普通响应的 32KiB 缓冲；不改变每次写出即 flush 的语义。
- 100 Key 下新策略 acquire/release 约 1.0–1.1µs、零分配；单次窗口采样约 40–75ns、零分配。
- 大规模全量探索扫描是 O(N)：1000 Key 约 10µs，10000 Key 约 120µs；小白名单扫描与池大小基本无关。统计快照（管理/周期统计用）随字段增多变大，100 Key 约 27KB。

复现微基准：

```sh
go test ./internal/balancer -run '^$' -bench 'Benchmark(RecentRecordSample|Pool|ExplorationScale)' -benchmem
go test ./internal/gateway -run '^$' -bench 'Benchmark(AggregateChildLoadScore|Router_StubTransport|Router_ServeHTTP|ResponseCopyBuffer)' -benchmem
```

微基准不代表生产 QPS/P99。

## 7. 当前链路与剩余优化建议

当前普通链路：路由 → 客户端鉴权 → 有界请求重放准备 → 选 Key → URL/头改写 → HTTP Transport → 错误分类/重试 → 转发。
聚合入口在上面增加 child 的优先级/权重选择，复用同一 `requestExecution`。

已落实的治理（详见 [架构与升级](architecture.md)）：配置变更串行化并先持久化后发布、Key 状态跨路由重建共享、
状态日志脱敏、Transport 跨热更新复用。剩余优化按建议优先级排列，均**未**实施：

| 优先级 | 现状 | 建议 |
|---|---|---|
| P1 统计规模 | 周期 Flush 仍复制所有 KeyState；管理端拿所有 vendor stats 后再过滤；前端分页不减少响应量 | 增加轻量统计快照/脏 Key 跟踪、后端按供应商过滤；先用 1千/1万 Key 压测再选方案 |
| P1 数据库写成本 | PG 每个变化 Key 一次 UPDATE（事务批量）；文件驱动变化时整文件重写 | Key 规模较大时再改 `UPDATE FROM VALUES`/批协议；文件可考虑更长可配置 Flush 或日志结构 |
| P1 可观测性 | 只有累计计数和 5 样本均值，没有生产级 P95/P99、每下游请求的上游尝试数、持久化延迟/失败指标 | 少量聚合计数/直方图，避免逐请求日志 |
| P2 链路复杂度 | 聚合重试仍经 callback 穿透内部循环，错误分支多（全局尝试预算已修复为单一计数） | 先统一 attempt outcome，再考虑候选迭代器；保持 child 优先级/权重、已提交响应不重试等不变量 |
| P2 冷却信号 | 网关自身合成的 503（全部冷却）不带 `Retry-After`；冷却中的候选集会让请求毫秒级尝试下一个 Key | 候选集全冷却时直接返回 429 + 最早 `CooldownUntil` 换算的 `Retry-After`（属可观测行为变更，需确认下游可接受） |
| P2 后台负担 | 热更新全量 ListAll / 重建，UI 自动刷新获取全量统计 | 增量更新配置、可见页刷新/查询范围收窄 |

不建议为"精简"直接删除鉴权、请求重放边界、错误真实状态分类、流式 idle timeout 或错误 masking：这些承担不同功能。
真实吞吐、长流并发、数据库往返时延、多实例一致性仍需独立压测/集成测试。
