## 1. 已实现的统计语义

统计单位是 **(vendor ID, 托管 Key) 的一次上游尝试**，不是一个客户端请求，也不是 TCP 包。
一次客户端请求若故障转移到两个 Key，会分别产生两个 Key 的样本。passthrough 不保存客户端 Key 的统计。

| 字段 | 含义 |
|---|---|
| `recent_requests` | 最近有效尝试数，上限 5，按完成顺序滚动 |
| `recent_success_count` | 窗口内成功次数：HTTP <400，完整转发至 EOF，且不是异常空响应 |
| `header_samples` / `avg_header_ms` | 窗口中头耗时/失败惩罚样本数及均值（毫秒） |
| `response_samples` / `avg_response_ms` | 窗口中整包耗时/失败惩罚样本数及均值（毫秒） |

计时起点紧邻 `http.Client.Do`，不含客户端请求体预缓冲、鉴权和 Key 选择。
头耗时含连接池等待、DNS/TCP/TLS、请求上传及上游等待，**不是首字节精确追踪，更不是 LLM 首 token 耗时**。
整包耗时计到读取 EOF，流式请求计到流结束；因读取与写出串行，包含先前的下游背压，不等于纯上游生成速度。

- HTTP 错误（含 502/504）、网络失败、重试丢弃的错误响应、上游 body 超时/断流：每次记录失败，头和整包均使用 **999 秒（999000ms）**，无论是否收到响应头、是否读到 EOF。均值包含惩罚，不是纯真实延迟。
- 成功响应仍记录真实头/整包耗时。JSON/SSE 或常见推理接口的 0B 响应判失败；HEAD、OPTIONS、204/205、304、重定向和通用接口允许的空响应不误判。不解析 SSE 结束事件或业务 token。
- 客户端取消及下游写失败记录一次累计请求，不记成功/上游错误、不进入近期窗口、不更新健康或最近错误。`interrupted_count` 由 `total_requests - success_count - 各类错误计数` 推导，无新数据库列；界面单独展示，成功率排除该部分。
- 收到成功头后的上游 body 超时/断流现在也增加累计错误，执行 request-error 健康策略并记录网关 502 诊断。已知 HTTP 错误保留真实状态，即使错误体读取或下游交付随后失败。
- 每个 attempt 通过 `finish` 只结算一次，重试、masking 和下游取消不重复计数。body 超时只计上游读取等待，不计下游 Write/Flush；真正读取超时即使由 Close 唤醒为 EOF，也不会误判为成功或客户端取消。
- 不保存请求内容、响应内容、逐请求数据库记录或无限增长的时间序列。历史漏记不可恢复；已聚合的旧均值不伪造回填，窗口随新尝试更新。

实现：`internal/balancer/performance.go` 固定 `[5]requestSample`，无堆分配；最多重算 5 个值。
`internal/gateway/attempt_timing.go` 统一结算计数和采样，成功 EOF 时间在响应转发循环中捕获，不再依赖响应体 Close/上下文状态推断结果。不增加每请求 goroutine、timer 或响应缓冲。

### 缓存与持久化

沿用 `RuntimeStatsPersister` 默认 5 秒周期及关闭时最终 Flush：无变化不写，发生变化随现有统计同批写入。
累计计数仍用 delta 累加，近期统计是**覆盖快照**，不是平均值累加。特别处理了“只有近期窗口变化、累计计数未变”的情况，不清除最近状态码/错误。
明确失败时不推进 persister 基线；文件存储继续先成功写盘再交换内存，测试覆盖失败重试不重复累加。

均值与样本数保存在文件 JSON / PGSQL `recent_stats JSONB` 中，**原始五条样本只在内存**。
热更新复用 registry handle，仍存在的 Key 的在途请求完成后也能写回同一窗口。
重启会保留最后持久化的摘要作展示及策略初始参考；第一条新样本或相隔 5 分钟后的新样本开始建立新窗口，不用历史均值伪造 5 条样本。

边界：

- 无流量时保留最后的窗口，并非“最近几分钟”；不是长期监控或告警系统。
- 崩溃/SIGKILL 仍可能丢失最近一个尚未刷盘窗口，与现有累计统计一致；没有增加 WAL。
- 多实例共享数据库时，这个摘要是各实例最近写入的本地窗口，**不是所有实例合并后的全局最近 5 次**。
- PG 事务提交结果不明的幂等性问题沿用现有计数增量协议，本次未引入分布式 exactly-once。

## 2. 三种新策略

令 `H` 为成功样本的平均头耗时，`F` 为成功样本的平均整包耗时，`I` 为当前在途请求数，
`p = (近期成功数 + 1) / (近期尝试数 + 2)` 为拉普拉斯平滑成功率。
成本越低越优先：

| 策略 | 常规成本 | 场景 |
|---|---|---|
| `lowest_latency` | `H × (I + 1) / p` | 流式对话、优先快速开始响应 |
| `highest_success` | `(I + 1) / p²` | 对成功率更敏感，仍考虑当前负载 |
| `adaptive` | `(0.7H + 0.3F) × (I + 1) / p²` | 相近模型/输出长度的非流式业务 |

展示均值包含失败的固定 999 秒惩罚；调度耗时只使用成功样本，配合已有成功率/全失败惩罚，不重复把 999 秒代入调度耗时。重启后的持久化摘要没有成功耗时明细，只有全成功摘要可恢复耗时评分，混合摘要使用中性耗时和已有成功率。

无头耗时时使用 1000ms 初始参考；无整包耗时时用 H。策略计算的 H/F 限制在 1ms–1h，F 不小于 H；展示均值不做这个截断。
有样本但窗口成功数为 0 时，三种策略的基础成本统一提升到 `1e12`，避免“失败越快越被偏好”。
在全无成功候选时仍能选择可用 Key；不是另一个硬熔断器。

保护机制：

1. 每次成功选择累积一份探索预算，累积 10 份可探索一次，最多保留一次额度。当前白名单没有待探索候选时保留额度，不固定在第 10 次请求消耗。预算在重叠路由代际间共享。
   无样本 Key 补足 2 次有效样本，5 分钟无新样本的 Key 重新评估；按上次实际选中时间从旧到新分配机会，取消也更新尝试顺序，但不记失败样本。只探索当前无在途请求的 Key。
   连续失败的探索退避为 1/2/4/5 分钟（上限 5 分钟），成功清除；这只限制探索，正常评分仍可在没有更好候选时选择它。
   最后采样后 5–10 分钟，旧评分线性回归中性值；下一次过期采样重新建立窗口。重启无采样时间可恢复，摘要最多作为启动后 10 分钟的初始参考，并立即参与补样。
   探索使用真实请求，不新增后台上游调用。N 个待探索 Key 在每分钟 R 次合适选择下，一轮约需 10N/R 分钟；没有流量不能保证按时刷新。
2. 探测与普通选择均遵守：禁用、冷却、已尝试排除、聚合 child 的 Key 白名单；空白名单仍禁止选择。
3. 相同成本按轮询距离打破平局。无新增随机数依赖或控制台调参旋钮。
4. 基础成本只在样本完成时重算。一次扫描同时寻找最低成本与待探索候选，每候选读取一个成本原子数并判断过期，不增加逐 Key 统计锁、堆分配、计时器或后台 goroutine。
5. 原四种策略及默认 `round_robin` 保留，不自动改现有配置。
6. 新策略仅用于托管 Key 选择；聚合供应商应在 child 上配置。后端拒绝在 aggregate 上静默接受却不执行它们。

限制：5 样本的小窗口响应快但较噪；请求模型、token 数、客户端速度不一致会影响比较。
尤其长流式响应本来就可能持续很久，不宜直接用整包时长评价上游速度，优先考虑 `lowest_latency`。
“高成功率优先”不是绝对只选成功率最高者：并发惩罚可能让空闲候选获得流量。

## 4. 已落实的网关小优化与对照

### A. 聚合负载评分不再复制完整 KeyState

`aggregateChildLoadScore` 原来为每个 child 调用 `Pool.Snapshot()`：即便只需要两个计数，也会复制全部 KeyState 并逐个加 stats 锁。
改为 `Pool.LoadTotals(allowed)`，只读并发与原子累计请求数，支持按 child 的 Key 子集扫描。
保留原有评分、权重和优先级语义，禁用/冷却键的计数统计范围也与之前一致。

### B. 流式复制复用独立 4KiB 缓冲池

原来每条流分配 4KiB；现在用独立 `sync.Pool`。**没有让长流占用 32KiB 普通响应缓冲**。
不改变每次写出即 flush 的语义，不合并 SSE 事件或增加发送延迟。

### C. 压缩错误预览解压有界

原始错误预览限制为 2048 字节，但 `maybeDecompressPreview` 原先无限制解压，且 deflate reader 未关闭。
现在解压诊断文本上限 64KiB，同时关闭 deflate reader，避免小压缩体产生过大的内存分配。
这是诊断预览的限制，不截断实际透传响应；超出部分不参与关键词分类。

## 5. 当前链路、冗余与剩余优化建议

当前普通链路：路由 → 客户端鉴权 → 有界请求重放准备 → 选 Key → URL/头改写 → HTTP Transport → 错误分类/重试 → 转发。
聚合入口在上面增加 child 的优先级/权重选择，但复用请求级 `requestExecution`。

旧 `architecture-review.md` 中部分结论已过期，本次重新核查确认：

- 请求级全局预算与已尝试 Key 集合已经存在；默认上游尝试预算 10、配置上限 100，不应继续称其为无共享预算的双层相乘。
- 成功响应不参与聚合重试；非幂等 POST 的 5xx/网络错误仍不重放。
- `transportManager` 已跨热更新复用 Transport（按配置区分，Transport 内部再按主机管理连接），过期配置关闭空闲连接。
- 非幂等重试状态码谓词已合并。仍有双层循环/回调，不等于所有旧缺陷还存在。

建议按下面优先级继续处理，本次**未**进行高风险控制面/路由重构：

| 优先级 | 现状与证据 | 建议 |
|---|---|---|
| P0 一致性 | `admin/service.go` 的 RMW 没有服务级串行化，`UpdateConfig` 先更新 runtime 后持久化 | 串行化整段配置变更；确定持久化/发布的提交顺序并做失败注入测试，而不是只加 Store 内存锁 |
| P0 日志安全 | `keystore/async_store.go` 的状态写失败日志仍拼接原始 Key | 使用 KeyID；区分版本冲突、持久化失败并可观测化 |
| P1 状态生命周期 | 统计 handle 跨重载，但 inflight/冷却仍在 Pool 上；reload 不复制 inflight，以避免旧池释放导致泄漏 | 将并发和健康状态也提升到共享 handle；否则热更新期间新策略暂时低估已有负载，且快照后的旧池健康变化可能遗漏 |
| P1 统计规模 | 周期 Flush 仍复制所有 KeyState；管理端拿所有 vendor stats 后再过滤；前端分页不减少响应量 | 增加轻量统计快照/脏 Key 跟踪、后端按供应商过滤；先用 1千/1万 Key 压测再选方案 |
| P1 数据库写成本 | PG 每个变化 Key 一次 UPDATE，事务批量但不是网络层单条批更新；文件驱动变化时整文件重写 | Key 规模较大时再改 `UPDATE FROM VALUES`/批协议；文件可考虑更长可配置 Flush 或日志结构，不能简单缩短周期 |
| P1 可观测性 | 有累计 Key 统计，但没有生产级 P95/P99、每下游请求的上游尝试数、持久化延迟/失败指标 | 少量聚合计数/直方图，避免逐请求日志；本次五样本均值不能替代这些 |
| P2 链路复杂度 | 聚合重试仍经 callback 穿透内部循环，错误分支多；安全预算已修复 | 先统一 attempt outcome，再考虑候选迭代器；保持 child 优先级/权重、已提交响应不重试等不变量，不一次性拍平改写 |
| P2 后台负担 | 热更新全量 ListAll / 重建，UI 自动刷新获取全量统计 | 增量更新配置、可见页刷新/查询范围收窄；保持本次同一份响应式表格，避免再维护移动/桌面两份 DOM |

不建议为“精简”直接删除鉴权、请求重放边界、错误真实状态分类、流式 idle timeout 或错误 masking：这些承担不同功能。
